# ジム記録アプリ 設計書

作成日: 2026-08-14

## 1. 概要

10人以下の閉じたグループで使う、筋トレ記録用のWebアプリ（PWA）。
メンバー全員が互いの記録を閲覧できる。

**成功条件: トレーニング中に1セットを2タップで記録できること。**

この条件を設計判断の基準とする。機能追加とこの条件が衝突した場合、機能を落とす。

## 2. 対象ユーザー

- 管理者（アプリ作成者）が発行したアカウントを持つ10人以下のメンバー
- 全員が筋力トレーニングを行う。有酸素運動は対象外
- 利用場面はジムの現場。片手操作、短い休憩時間、汗をかいた手

## 3. スコープ

### MVPに含む

- メール/パスワードによる認証
- ワークアウト記録（種目・重量・回数・セット）
- 種目マスタ（プリセット約50種 + 自作種目の追加）
- 前回値の自動プリフィル
- グループフィード（全員の直近の記録を時系列表示）
- 自分の履歴（カレンダー + セッション一覧）
- 種目別の重量推移グラフと自己ベスト表示
- メンバー一覧および各メンバーの履歴閲覧
- 設定（表示名の変更、ログアウト）

### MVPに含まない

以下はMVPでは実装しない。将来の追加は可能だが、本設計書の範囲外とする。

- 有酸素運動の記録
- 体重・体脂肪などの身体記録
- インターバルタイマー
- ルーティン/メニューのテンプレート機能
- プッシュ通知およびリマインダー
- オフライン対応とデータ同期
- いいね、コメントなどのソーシャル機能
- 一般公開のユーザー新規登録

ルーティンテンプレート機能は「前回値の自動プリフィル」で価値の大半を代替できるため、
MVPでは前回値プリフィルのみを実装する。

### 将来の追加候補

MVP完成後に追加する意向が確認されている機能。本設計書では実装しないが、
以下を妨げる設計判断は行わない。

| 機能 | 追加時の影響範囲 |
|---|---|
| 体重・体脂肪の記録 | `body_measurements` テーブルを1つ追加。既存テーブルの変更は不要 |
| インターバルタイマー | 記録画面内で完結するクライアント側の機能。DB変更は不要 |

## 4. 技術構成

| 層 | 選定 |
|---|---|
| フロントエンド | Vite + React + TypeScript |
| スタイル | Tailwind CSS |
| PWA | vite-plugin-pwa |
| バックエンド | Supabase（PostgreSQL + Auth + Row Level Security） |
| グラフ | Recharts |
| ホスティング | Vercel |
| テスト | Vitest（ロジック） / Playwright（E2E） |

### 選定理由

サーバーサイドレンダリングを持たないSPAとする。利用者が10人でSEOが不要なため、
Next.jsのApp Routerが持つサーバー/クライアント境界や認証Cookieの複雑さを
負担する理由がない。構成を単純に保ち、実装時間をUIの作り込みに配分する。

バックエンドはSupabaseに委ね、独自のAPIサーバーは持たない。認証・DB・アクセス制御を
managedな仕組みで賄い、フロントエンドのコードだけを保守対象とする。

## 5. データモデル

### テーブル定義

**profiles**

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | `auth.users.id` への参照 |
| display_name | text | 表示名 |
| created_at | timestamptz | 作成日時 |

**exercises**

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | |
| name | text | 種目名 |
| name_normalized | text | 重複検出用の正規化名（小文字化・空白除去） |
| muscle_group | text | 部位（chest / back / legs / shoulders / arms / core） |
| is_preset | boolean | プリセット種目かどうか |
| created_by | uuid (FK, nullable) | 自作種目の作成者。プリセットはnull |
| created_at | timestamptz | |

**workouts**

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | |
| user_id | uuid (FK → profiles) | |
| performed_at | timestamptz | トレーニング実施日時 |
| note | text (nullable) | メモ |
| created_at | timestamptz | |

1回のジム訪問が1レコードに対応する。

**workout_sets**

| カラム | 型 | 説明 |
|---|---|---|
| id | uuid (PK) | |
| workout_id | uuid (FK → workouts) | |
| exercise_id | uuid (FK → exercises) | |
| set_index | integer | セット順（1始まり） |
| weight_kg | numeric(5,1) | 重量 |
| reps | integer | 回数 |
| created_at | timestamptz | |

`workouts` と `workout_sets` は1対多。「ベンチプレス80kg×8回×3セット」は
`workout_sets` の3レコードとして保存する。この形式により、セットごとに
重量や回数を変える記録方法にも対応できる。

### アクセス制御（Row Level Security）

| 操作 | ポリシー |
|---|---|
| SELECT | 認証済みユーザーは全レコードを読める |
| INSERT | 自分の `user_id` のレコードのみ作成できる |
| UPDATE / DELETE | 自分が作成したレコードのみ |

`workout_sets` は `user_id` を持たないため、親の `workouts.user_id` が
現在のユーザーと一致することを条件にポリシーを定義する。

`exercises` のプリセットは全ユーザーが読み取り専用で参照する。自作種目は
作成者のみが編集・削除でき、閲覧は全員が可能。

グループの閉鎖性は、Supabaseの一般公開サインアップを無効化し、
管理者がダッシュボードから10人分のアカウントを発行することで担保する。
招待コードなどの独自機構は実装しない。

## 6. 画面構成

| # | 画面 | 内容 |
|---|---|---|
| 1 | ログイン | メール/パスワード |
| 2 | ホーム（フィード） | 全員の直近の記録を時系列表示。最上部に「トレーニング開始」ボタン |
| 3 | 記録画面 | 種目選択とセット記録。アプリの中核 |
| 4 | 自分の履歴 | カレンダー + セッション一覧 |
| 5 | 種目詳細 | 重量推移グラフ、自己ベスト、総ボリューム |
| 6 | メンバー | メンバー一覧から各人の履歴へ |
| 7 | 設定 | 表示名の変更、ログアウト |

## 7. 中核導線

```
「トレーニング開始」
  → 種目を選ぶ（最近使った種目を上位に表示）
  → セット記録画面
       重量 [ 80 ] kg    ← 前回値をプリフィル
       回数 [  8 ] 回    ← 前回値をプリフィル
       [ − ][ + ]        ← 調整が必要なときのみ操作
       ┌──────────────┐
       │  セット完了   │  ← 画面最下部に固定、高さ64px
       └──────────────┘
  → 完了したセットが画面上部に積み上がる
  → 種目を追加、または「終了」
```

前回と同じ重量・回数であれば「セット完了」の1タップで記録が完了する。
調整が必要な場合も ± ボタンの操作と1タップで済む。

数値入力時にソフトキーボードは原則表示しない。数値部分を直接タップした
場合のみ、直接入力を許可する。

重量の増減単位は2.5kg、回数は1回を既定とする。

## 8. UI原則

ダーク、ストイック、実用重視。

- 背景はほぼ黒。ジムの照明環境下で数値が読めるよう高コントラストを維持する
- 主要な操作ボタンは画面下部の親指到達圏に配置し、タップ領域は最小56px
- 重量と回数の数値を画面上で最も大きく表示する
- 色数を絞る。アクセント色1色を「セット完了」と「自己ベスト更新」にのみ使用する
- アニメーションは最小限に留め、操作への即応性を優先する

## 9. エラー処理

「記録できたか分からない」状態を最も重大な障害として扱う。

| 事象 | 対応 |
|---|---|
| 保存失敗（通信断など） | トーストで明示し再試行ボタンを表示。入力値は保持し消さない |
| 保存成功 | 楽観的に画面へ反映しつつ、保存確定をチェック表示で明示する |
| 認証セッション切れ | ログイン画面へ誘導。記録中のデータはローカルに保持し、復帰後に継続する |
| 自作種目の重複作成 | `name_normalized` で既存種目を検索し、候補をサジェストする |

オフライン対応は行わないため、通信不可の状態では記録できない旨を明示的に表示する。

## 10. コード構造

機能単位でディレクトリを分割する。各機能は独立して読解でき、
Supabaseへの問い合わせは各機能のクエリ層に閉じ込める。

```
src/
  features/
    auth/          ログイン、セッション管理
    workout-log/   記録画面（中核）
    feed/          グループフィード
    history/       自分の履歴、メンバーの履歴
    exercises/     種目マスタ、種目詳細、グラフ
  components/ui/   共通UIコンポーネント
  lib/
    supabase.ts    Supabaseクライアント
    calc.ts        自己ベスト・ボリューム等の計算ロジック
```

計算ロジック（`lib/calc.ts`）はSupabaseに依存させず、純粋関数として実装する。
これによりテストが単体で完結する。

## 11. テスト方針

| 種別 | 対象 |
|---|---|
| Vitest | 自己ベスト算出、総ボリューム計算、前回値取得ロジック |
| Playwright | 中核導線1本（ログイン → セット記録 → フィードへの反映） |
| RLSテスト | 他ユーザーの記録を更新・削除できないことの確認 |

E2Eは中核導線1本に絞る。網羅よりも、最も壊れて困る経路が常に動くことを担保する。

## 12. 用語定義

| 用語 | 定義 |
|---|---|
| セット | 種目・重量・回数の1組。記録の最小単位 |
| ワークアウト | 1回のジム訪問。複数のセットを含む |
| 自己ベスト | ある種目における、そのユーザーの最大重量 |
| 総ボリューム | 重量 × 回数 の合計値 |
| 前回値 | 同一ユーザー・同一種目における直近のセットの重量と回数 |
