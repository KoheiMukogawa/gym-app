# ご意見・不具合の報告 設計

作成日: 2026-10-05

## 目的

利用者が、気になる点や改善してほしい点を、思いついたその場でアプリから運営に送れるようにする。運営（管理者）はアプリ内で新着に気づき、読み、既読にできる。

成功の基準:

- 利用者が数タップで意見を送れる。送った意見が運営に読まれたかが分かる
- 送った意見は、本人と管理者以外には見えない
- 管理者はアプリを開くだけで新着の有無に気づける

対象外: 運営からの返信、対応状況（検討中・対応済みなど）の表示、利用者同士で意見を見せ合うこと、メールやプッシュでの通知、画像の添付、分類（不具合・要望など）の選択、意見の削除・編集。

## 決めたこと

- **運営にだけ届く投書箱にする。** 他の利用者には見せない。書きにくい不具合報告も送ってもらいやすくするため
- **新着は管理者だけにアプリ内で表示する。** メール送信の基盤（独自ドメイン・SMTP）がまだないため、通知はしない
- **管理者は別テーブル `public.admins` で判定する。** `profiles` は本人が更新できるため、権限の情報を置かない。登録はSQL Editorで行う
- **管理者の操作はDB関数（security definer）で行う。** `profiles` のRLSは本人の行しか読めないため、送信者の名前を一覧に出すには関数で結合する必要がある。既読にする操作も関数に寄せ、`feedback` への更新権限は誰にも与えない
- **送信時にブラウザ情報（`navigator.userAgent`）を添える。** 不具合の調査に使う。送信画面に添えることを明記し、プライバシーポリシーにも書く

## DB（migration 1本）

### `public.admins`

| 列 | 型 | 内容 |
|---|---|---|
| `user_id` | uuid primary key | `profiles(id)` を参照、on delete cascade |
| `created_at` | timestamptz not null default now() | |

RLSを有効にし、`select` だけを許可する（`user_id = (select auth.uid())`、本人の行だけ）。アプリはこれで自分が管理者かを判定する。insert・update・deleteのポリシーは作らない（アプリからは書けない）。

### `public.feedback`

| 列 | 型 | 内容 |
|---|---|---|
| `id` | uuid primary key default gen_random_uuid() | |
| `user_id` | uuid not null | `profiles(id)` を参照、on delete cascade。default `auth.uid()` |
| `body` | text not null | 前後の空白を除いて1〜2000文字（check制約） |
| `user_agent` | text | 500文字以下（check制約） |
| `created_at` | timestamptz not null default now() | |
| `read_at` | timestamptz | 管理者が既読にした日時。未読はnull |

インデックス: `(user_id, created_at desc)`、未読の一覧用に `(created_at desc) where read_at is null`。

RLS:

- `insert`: `user_id = (select auth.uid())` かつ `read_at is null`
- `select`: `user_id = (select auth.uid())`（本人の分だけ）
- update・deleteのポリシーは作らない

退会すると `profiles` からの連鎖で消える。退会の関数（`delete_my_account`）は変えない。

### 送信の上限（トリガー）

`before insert` のトリガーで、同じ `user_id` の直近24時間の件数が10件以上なら例外（`'送信の上限に達しました。時間をおいてお試しください'`）。

### `admin_list_feedback() returns table(...)`

管理者向けの一覧。security definer、空search_path、完全修飾名。

1. `auth.uid()` がnullなら例外（`'ログインが必要です'`）
2. 呼び出した人が `admins` にいなければ例外（`'権限がありません'`）
3. `feedback` を `created_at desc` で最大200件、`id`・`body`・`user_agent`・`created_at`・`read_at`・送信者の `display_name` を返す

### `admin_unread_feedback_count() returns integer`

管理者でなければ0を返す（例外にしない。プロフィール画面で毎回呼ぶため）。管理者なら `read_at is null` の件数を返す。security definer、空search_path。

管理者かどうかは `admins` の `select` で判定し、この関数は件数のためだけに使う（新着0件の管理者にも一覧への入口を出すため）。

### `admin_mark_feedback_read(p_id uuid) returns void`

管理者でなければ例外（`'権限がありません'`）。`read_at` がnullの行だけ `now()` にする（既読の行はそのまま）。

権限: 3つの関数とも `public`・`anon` から実行権を外し、`authenticated` にだけ付与する。advisorsの `authenticated_security_definer_function_executable` は3件増えるが、設計どおりのものとして扱う（CLAUDE.mdの既知の一覧に追記する）。

## 画面

### 入口（プロフィール画面）

「アカウント」欄の上に「ご意見」欄を追加する。

- 「ご意見・不具合を送る →」（`/feedback`）。タップ領域56px
- 管理者にだけ「届いた意見 →」（`/admin/feedback`）。新着があれば件数のバッジ（例: 「新着 3」）を付ける。管理者の判定や件数の取得に失敗したときは、この行を出さない（利用者の画面を壊さないため。管理者は一覧画面でエラーに気づける）

### 送信画面 `/feedback`

ログインが必要。`AppShell` の中に置く。

1. 見出し「ご意見・不具合の報告」
2. 説明: 「気になる点や、こうしてほしいという要望を運営に送れます。内容は運営だけが読み、ほかの利用者には表示されません。個別の返信はできないことがあります。」
3. 本文の入力欄（複数行、2000文字まで、残り文字数を表示）
4. 注記: 「不具合の調査のため、お使いのブラウザの情報（機種・OSの種類など）も一緒に送られます。」
5. 「送信する」ボタン（56px）。本文が空白だけなら押せない
6. 「送った意見」: 自分の送信履歴を新しい順に表示（最大50件）。各行に日時と本文、既読のものには「運営が確認済み」

状態:

- 送信中は入力欄とボタンを無効にし、ボタンの文言を「送信中…」にする
- 成功したら入力欄を空にし、トースト「送信しました。ありがとうございます」を出して、履歴の先頭に加える
- 失敗したら画面内にエラーを出し、入力した本文は残す
- 履歴の読み込みに失敗したら、履歴の欄にエラーと「再試行」を出す。送信フォームはそのまま使える

### 管理者の一覧画面 `/admin/feedback`

ログインが必要。`AppShell` の中に置く。管理者でなければ関数が「権限がありません」を返すので、そのエラーを画面に出す（ルートでの出し分けはしない）。

- 見出し「届いた意見」と未読件数
- 新しい順の一覧。未読の行は背景色で目立たせる
- 各行: 送信者の名前、日時、本文（改行を保つ）、ブラウザ情報（小さい文字）、未読なら「既読にする」ボタン（56px）
- 「既読にする」を押したら、その行だけ既読の表示にする。失敗したら行内にエラーを出し、ボタンを戻す
- 読み込み中はスピナー、失敗したら画面内にエラーと「再試行」
- 0件なら「まだ意見は届いていません」

## エラー表示

- 通信エラーは既存の `toMessage` の文言を使う
- DB側の例外の文言（`ログインが必要です`、`権限がありません`、`送信の上限に達しました。時間をおいてお試しください`）はそのまま表示する
- 関数やテーブルが見つからない（`PGRST202`・`PGRST205`）場合は「この機能の準備中です。時間をおいてお試しください。」と表示する

## プライバシーポリシー

- 「1. 取得する情報」の「利用者が入力・設定する情報」に「ご意見・不具合の報告: 送った内容と、送信時のブラウザの情報」を追加する
- 「3. ほかの利用者に表示される情報」の、ほかの利用者に表示されないものの列挙に、送った意見を加える
- 制定日の下に改定日を加える

## テスト

- SQL（`supabase/tests/feedback.sql`、`run-sql.mjs` の対象に追加）:
  - 本人は自分の意見を送れて読める。他人の意見は読めない
  - `user_id` に他人を指定した送信、`read_at` を入れた送信は拒否される
  - 本文が空白だけ・2001文字以上は拒否される
  - 24時間で11件目は例外になる
  - 本人は `feedback` を更新・削除できない。`admins` に書き込めない
  - 管理者でない人の `admin_list_feedback`・`admin_mark_feedback_read` は例外、`admin_unread_feedback_count` は0
  - 管理者は全件を送信者の名前付きで読め、既読にでき、未読件数が減る
  - `anon` は3つの関数を実行できない
  - 退会（`delete_my_account`）すると本人の意見と `admins` の行が消える
- 単体テスト: 送信画面（送信・空入力で押せない・失敗時に本文が残る・履歴と「運営が確認済み」・履歴の再試行）、管理者の一覧（表示・既読にする・権限エラー・0件）、プロフィール画面の入口（管理者だけに「届いた意見」とバッジ）
- モックE2E: プロフィール→送信画面→送信→履歴に出る

## 公開の順序

1. 実装し、lint・SQL・単体・モックE2Eを通す
2. migrationの内容を本人に見せ、許可を得て本番に適用する
3. 本番でテーブル・ポリシー・関数・実行権限ができたことを読み取りで確認する
4. 本人の許可を得て、本人のアカウントを `admins` に登録する（SQL Editorで1行）
5. アプリのコードをpushする（`git fetch` してから）。テーブルがないまま画面だけ公開されるのを防ぐため、migrationの適用より後にする
6. 本人が実機で1件送り、管理者の一覧で読んで既読にできることを確認する
