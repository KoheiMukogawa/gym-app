## 変更

- `public.my_big3_data()` は本人の対応設定、プリセット・対応先種目（最大6件）、実際に選択された最大3種目の全セットを1つのJSONとして返す。
- `SECURITY INVOKER`、空の`search_path`、本人の`auth.uid()`による絞り込みを使う。既存RLS・テーブルの権限は変更しない。関数の実行権限は`authenticated`のみ。
- セットは重量・回数・実施日時だけを返す。推定1RM・PR・グラフの集計は既存の`buildStrengthSnapshot`を使う。
- `fetchStrengthSnapshot`の呼び出し方とホーム・BIG3のコードは維持する。通信エラーや不正な応答を空の記録として扱わない。
- 記録画面は初めて`/log`を開くまでマウントしない。その後はタブ移動でも保持する。直接URLを開く場合と、保存済み下書きからの自動再開にも対応する。
- 結果のキャッシュ、全画面のコード分割、読み込み表示の変更は今回の対象外。

### 起動比較

公開版のソース（`e0954e5`）と変更後を、それぞれ本番用ビルド・Edge・390×844のモバイル表示で比較。合成した1003セット、API応答ごとに300msの遅延、各3回。認証セッションはテスト用のものを保存し、実ユーザー・本番APIを使わない。

| 指標 | 変更前 | 変更後 |
|---|---:|---:|
| BIG3取得の通信 | 4回 | 1回 |
| 起動時のデータ取得（プロフィール・認証・OPTIONSを除く） | 15回 | 6回 |
| ホーム表示後にBIG3を待つ時間の中央値 | 1029ms | 59ms |
| 同待ち時間の3回の結果 | 1865 / 978 / 1029ms | 89 / 59 / 37ms |

開発版のStrictModeはeffectを再実行するため、この比較には用いない。
この結果はモックの通信待ち時間の比較であり、iPhoneの実測値、実DBの処理速度、実APIの制限の検証ではない。
別の最終確認では変更後の待ち時間279ms、起動時データ取得5回だった。計測には端末負荷と認証・effectのタイミングによる変動があるため、上記中央値を実機の保証値とは扱わない。

## 本番反映の順序（本人の明示許可後）

1. `20261002130346_my_big3_data.sql`をSupabaseへ適用する。関数追加と実行権限・schema cache通知のみで、記録の更新はしない。
2. 本番の関数定義・実行権限・RLS・既存インデックスを確認する。本人のセッションでRPCを呼び、旧取得の件数・集計値との一致、JSONの返却、データ欠落がないことを確認する。ユーザーの記録や認証情報をログに出さない。
3. `EXPLAIN (ANALYZE, BUFFERS)`等で実DBの実行計画・処理時間を確認する。必要なインデックス追加はこの確認後に別途判断する。
4. 関数が利用可能になってからアプリをmasterへpushして公開する。先にアプリだけ公開するとRPCが未作成のためBIG3の取得が失敗する。
5. 本番iPhoneで新規起動・再起動・下書き再開・ホーム→BIG3→記録→ホームの導線を確認し、起動時の通信数と表示時間を測る。

一時PGliteにはPostgRESTがない。実APIを通した1000件超の確認は未実施で、本番の本人の件数が少ない場合には検証用API環境で合成データを使って別途確認する。本番へ合成データを追加しない。
